## 2. 时间不能只看一个 runtime

`first_feasible_sec` 是第一次不再使用人工行的时间；`best_found_sec` 是本次最终最好成本被记录的时间；`runtime_sec` 是程序结束时的总耗时。均从读取输入之前开始，不含编译与事后审计。

本次 case7 在约 10.01 秒已经得到最终最好值，仍继续搜索到约 120.22 秒。这不代表找到该值需要完整 120 秒，也不代表提前知道后面不会更好。

程序有软截止时刻，数据解析、匹配、候选扫描和检查之间可能产生少量超时。跑批端另设 watchdog。OS 文件页缓存可能已热，虽然程序不使用旧求解器的解析缓存，这仍不是严格冷启动测试；并行审计与服务器其他负载也可能影响轨迹。因此这些数字不是跨硬件或跨算法的严格速度排名。

## 3. 历史多轮最好结果

历史自写 solver 共做了 26 次正式运行，逐 case 保留实际最低成本：最大 gap 0.126074644%，平均 gap 0.035649618%。case1–4 各做 4 次，名义预算合计每例 780 秒；case5–9 各做 2 次，名义预算合计每例 300 秒。

它们来自 `round1`、`round2`、`focused`、`directed` 等实验，参数、种子和源码版本不同。这个表用于保存已经找到的方案，不是统一配置的单次测试，也不是由外部 HiGHS 生成的方案。

当前发布版在整理代码时增加了输入/输出保护、局部定价截止检查、统一的策略模式等处理，不是旧二进制的逐字重编译。限时搜索轨迹可能因此变化。不能用历史最好成绩给当前默认配置作保证。

历史实际方案与独立审计记录保存在 [历史目录](../results/historical)。旧代码与完整探索目录在开发工作区外备份，没有继续混入活动源码目录。

## 4. 正确性测试

常规测试通过 13 个测试方法，其中随机小实例测试包含 30 个独立实例，逐一与另外写的穷举程序核对最优成本与全局下界。另有必须打包、完全无 singleton、骑手增广链、负成本、零成本、重复行、三个模式、不可行输入、非法输入、旧结果保护、损坏证书拒绝和跑批入口测试。

穷举只用于很小的测试，不参与正式求解。正式结果的审计不导入任何求解代码。

开发服务器的 GCC 4.8.5 不支持完整 ASan/UBSan 配置，并缺少 ASan 运行库，因此该服务器的 sanitizer 尝试没有完成；不能列为通过项。随后已核对 GitHub Actions 的实际执行结果：提交 `7d970d0` 的 [运行 35214991639](https://github.com/xincy22/delivery-experiments/actions/runs/35214991639) 中，`make test` 与 `make sanitize` 均已成功完成，包括 AddressSanitizer / UndefinedBehaviorSanitizer 检查。这里记录的是实际运行结果，而不仅是工作流配置；摘要保存于 `results/release-20260917/ci.json`。

## 5. 如何复测

```bash
make test
python3 benchmark.py --output-dir outputs/reproduce \
    --time-limit-sec 120 --seed 1 --mode descent \
    --pricing-rounds 200 --workers 3 --verify
```

复测输出应放新目录。固定种子不会消除限时截止与机器负载的差异，因此请比较完整结果分布，不要求每条迭代轨迹逐位相同。

若比较算法改动，应固定机器、数据、种子集合、时间与节点预算，逐 case 配对记录，而不是只汇报每个版本的最好数。当前尚未做足以分离全局引导、局部下界和重匹配贡献的消融，不应把结果差异都归因于某一个组件。
